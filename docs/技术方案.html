1功能模块划分

建议 8 个模块，分 4 层。优先级从上到下递减，前 3 个是 MVP 必做，第 8 个可以最后补。

#模块职责关键难点
1用户画像与代谢引擎身高/体重/年龄/性别/活动量/目标 → 输出每日热量目标与三大营养素区间，管理过敏原与慢病禁忌公式选型与参数校验，异常输入拦截
2多模态饮食记录文本描述、语音、拍照、条码扫描四种入口，统一归一为「食物 + 克重」中文食物名歧义；估重误差
3食物成分与营养核算查成分表 → 按克重换算 → 汇总热量、宏量、微量营养素本地化数据；生熟重换算
4菜谱与食物推荐基于口味偏好、营养缺口、已有食材做候选排序冷启动（新用户无行为数据）
5膳食计划与排餐生成一日/一周三餐组合，输出采购清单多约束同时满足，易无解
6健康评估与风险预警GI/GL、钠、饱和脂肪、糖的超标检测；慢病禁忌冲突拦截规则要可解释、要能关闭
7可视化与反馈闭环体重趋势（需平滑）、达成率、周报、进度预测体重日波动 ±1kg，必须滤波
8营养知识问答 AgentLLM + RAG，引用权威指南回答营养问题幻觉控制；必须带出处
建议：把模块 1、3 做成纯确定性代码（无 LLM 参与），模块 2、4、8 才用模型。数值算错了用户会立刻失去信任，而且这类错误很难被发现。

2公式体系

这是系统的「物理定律」，必须硬编码 + 单元测试，绝不能让大模型口算。

2.1 基础体格指标

指标公式说明
BMIBMI = 体重kg ÷ 身高m²WHO 分级；中国标准偏瘦<18.5、正常 18.5–23.9、超重 24–27.9、肥胖 ≥28
标准体重(身高cm − 80) × 0.7（简易）仅作参考，不用于目标设定
腰臀比 WHR腰围 ÷ 臀围男 >0.90 / 女 >0.85 提示中心性肥胖
去脂体重体重 × (1 − 体脂率)有体脂率时，BMR 用 Katch-McArdle 更准

2.2 能量代谢（核心）

指标公式说明
BMR（首选）Mifflin-St Jeor：
男 10W + 6.25H − 5A + 5
女 10W + 6.25H − 5A − 161		W=kg, H=cm, A=岁。当前主流，比 Harris-Benedict 误差小
BMR（备选）Harris-Benedict（1919 原始 / 1984 修订）老项目常用，与旧文献对齐时用
BMR（有体脂）Katch-McArdle：370 + 21.6 × 去脂体重kg健身/低体脂人群更准
TDEEBMR × 活动系数久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高度 1.725 / 极高 1.9
活动消耗MET × 体重kg × 时长hMET 值查 2024 Compendium of Physical Activities
目标热量TDEE − 缺口，减脂建议 −300～−500 kcal/日硬性下限：男 ≥1500、女 ≥1200 kcal
热量↔体重1 kg 体脂 ≈ 7700 kcal用于进度预测：周减重 ≈ 缺口×7 ÷ 7700

2.3 营养素核算

指标公式说明
Atwater 系数蛋白 4 · 碳水 4 · 脂肪 9 · 酒精 7 kcal/g核算与反算的通用换算基准
蛋白质目标1.2 ~ 2.0 g/kg 体重（减脂期偏高）先定蛋白质，再定脂肪
脂肪目标0.8 ~ 1.0 g/kg 体重，且 ≥ 总热量 20%低于 20% 会影响激素与脂溶性维生素吸收
碳水目标(总热量 − 蛋白热量 − 脂肪热量) ÷ 4吃剩余热量
膳食纤维14 g / 1000 kcal（中国 DRIs 约 25–30 g/日）单独设下限约束
血糖负荷 GLGL = GI × 碳水g ÷ 100GL ≥20 高、11–19 中、≤10 低。比单看 GI 实用得多
供能比各宏量供能 ÷ 总热量中国居民膳食指南：碳水 50–65%、脂肪 20–30%、蛋白 10–20%
钠 / 钾钠 <2000 mg（≈5 g 盐）、钾 ≥2000 mg高血压人群的核心约束

2.4 体重趋势处理（易被忽略但很关键）

体重日波动可达 ±1 kg（水分、食物残留、衣着），直接连线会让用户误判。推荐：

  • 指数移动平均（EMA）：trendₜ = α·wₜ + (1−α)·trendₜ₋₁，α 取 0.1～0.2
  • 卡尔曼滤波：把真实体重当隐状态、日波动当观测噪声，效果更好且能给出置信区间
  • 代谢适应修正：实际周减重持续低于预测 50% 时，下调 TDEE 估计 5–10%（MacroFactor 的做法）

国内必备。开源整理版见 Sanotsu/china-food-composition-data，已转 JSON / SQLite，另附常见食物 GI 数据。
Open Food Facts
CC0，含条码，覆盖包装食品，有公开 REST API，适合扫码功能。
USDA FoodData Central
CC0，字段最规范，适合做成分表 schema 参考。
Food.com Recipes & Interactions
23 万菜谱 + 100 万条用户评分交互（Kaggle），推荐系统的标准 benchmark。
MealRec
1500+ 用户、7200+ 菜谱、3800+ 三餐组合，专做「一餐组合」推荐。
Nutrition5k
Google 发布，5000 道菜的多角度 RGB-D 图像 + 精确营养成分标注，图像估卡的标准数据集。
HowToCook
中文菜谱语料（Anduin2017/HowToCook），做中文菜谱库冷启动最省事。
中国居民膳食营养素参考摄入量（DRIs）
微量元素上下限的权威依据，别用美国 RDA 直接套。
版权提醒：《中国食物成分表》纸质版/电子版有版权，商用需授权；开源整理版属于社区二次加工，仅建议用于学习与非商业项目。USDA 与 Open Food Facts 是 CC0，可放心商用。

4算法选型

环节算法说明
食物名匹配中文分词 + 同义词表 + 编辑距离 + 向量召回不要只靠 embedding。「宫保鸡丁」和「宫爆鸡丁」这类变体靠同义词表最稳；向量召回做兜底
推荐（冷启动）TF-IDF + cosine 相似度（内容过滤）新用户无行为数据，只能靠菜品自身特征（食材、口味、营养、烹饪时长）
推荐（有数据后）协同过滤 / SVD 矩阵分解 / 双塔用户数过千、交互过万再上，否则不如内容过滤
推荐（最终）Hybrid：加权融合 + 重排序候选集用多路召回，排序层加业务规则（忌口硬过滤、重复度惩罚）
排餐优化整数规划（PuLP / OR-Tools）或贪心 + 回溯约束：热量区间、宏量区间、过敏原、忌口、7 天内菜品不重复、食材复用率
图像估营养多任务学习：食材多标签分类 + 质量回归 → 查成分表换算比「端到端回归热量」可解释、可纠错。Nutrition5k 上 SOTA 约 PMAE 17% 左右
体重趋势EMA / 卡尔曼滤波见 2.4
对话与解释LLM + RAG（向量检索 + BM25 混合，再重排）LLM 只负责组织语言，所有数字由确定性模块给出后注入 prompt
图像估重的现实预期：单张 RGB 照片估卡路里，当前开源方案误差普遍在 20–30%。产品上必须让用户能手动改克重，并明确标注「估算值」，不要假装精确。

6语言与技术选型

结论：Python 写算法与后端，TypeScript 写前端。不要为了"统一语言"用 Node 写模型服务——营养计算和推荐算法生态在 Python 侧，硬搬会浪费大量时间。

层选型理由
算法 / 后端Python 3.11+ · FastAPInumpy / pandas / scikit-learn / PyTorch / PuLP 全套现成；FastAPI 自带 OpenAPI 文档，调试快
Web 前端TypeScript · Next.js + Tailwind你要的科技感页面和图表（Recharts / ECharts）在 React 生态最成熟
移动端（可选）Flutter（Dart）若要 App，一套代码双端；但第一阶段建议只做 Web
数据库PostgreSQL + pgvector起步可先用 SQLite 单文件，量起来再迁。pgvector 省掉一个独立向量库
向量检索ChromaDB（本地） / Milvus（规模）RAG 菜谱检索；中小规模 ChromaDB 足够
模型服务PyTorch 训练 → ONNX Runtime 推理推理部署轻，CPU 也能跑
LLM 编排LangGraph / LlamaIndexLangGraph 做有状态的对话流程最顺手
部署Docker Compose一条命令起全套，交付和演示都方便
给你的务实建议：如果是课程项目 / 作品集，先做 Web（Python + FastAPI + Next.js），别一上来做 App。App 会吃掉你 60% 时间在打包、签名、适配上，而这些在评审里不加分。真正加分的是：营养计算准确、数据来源可追溯、交互有闭环。

7GitHub 开源参考

以下都实际存在，按「抄什么」分类。建议先读前三个。

simonoppowa/OpenNutriTrackerDart / Flutter · GPLv3 · 2.5k+ stars
最值得抄产品设计。它把每个公式都标了出处（热量用 IOM 2005、BMI 用 WHO、宏量用 WHO TRS 916、活动消耗用 2024 Compendium），App 内还有 Sources & References 页面。数据侧同时接了 Open Food Facts、USDA、德国 BLS。这种「每个数字都能溯源」的做法，是这个品类最该学的。
Sanotsu/china-food-composition-dataJSON / SQLite
做中文项目的关键资源。《中国食物成分表（第 6 版）》的营养素部分已 OCR 转成 JSON，并附了导入 SQLite 的脚本，另有常见食物 GI 数据。省掉你自己录几千条食物的工作量。
Decade-qiu/CookHero（亦见 petercao/CookHero）Python · FastAPI + React · Apache 2.0
最接近你要做的东西。LLM + RAG + 多模态 Subagent 的饮食管理 Agent，支持智能菜谱查询、个性化饮食计划、AI 饮食记录、营养分析、Web 搜索增强。技术栈 FastAPI + React + PostgreSQL + Milvus + Redis，还内置 ReAct 工具调用与 RAGAS 评估。架构可以直接参考。
RitamRixx/NutriGen_AIPython · LangGraph + ChromaDB
对话式收集画像 → 自动算 BMI/BMR/TDEE → RAG 检索 → 生成 7 天餐单。LangGraph 的 StateGraph 流程（profile_structurer → metrics_calculator → query_builder → diet_generator）写得非常清晰，适合照着搭你自己的对话流程。
CheeChoong14/Food-Recipe-Recommender-SystemPython · FastAPI + React
基于 Food.com 数据集的混合推荐：TF-IDF + cosine 做内容过滤，KNN 做协同过滤，再融合。代码量小、结构清楚，是推荐模块的现成骨架。
WUT-IDEA/MealRecPython · 数据集 + 模型
论文配套仓库，专做「一餐由前菜+主菜+甜点组成」的 bundle 推荐，提出了类别约束模型。想做组合排餐而不是单菜推荐时，这是最对口的参考。
AmirrrezaZ/dish2caloriesPython · EfficientNet + FastAPI
Nutrition5k 的复现实现：多标签食材分类 + 质量回归 → 查成分表换算营养。比端到端回归可解释得多，正是第 4 节推荐的路线。另可看 b010001y/Coase-to-Fine_Nutrition_Prediction 和 T0MYYY/Nutrition5k。
txxxxz/LightTableNext.js 15 + FastAPI
「冰箱里有什么 → 今天吃什么」的场景。SQLite 存偏好、LlamaIndex + ChromaDB 做菜谱检索、Mem0 做长期记忆。库存驱动推荐这个角度可以直接借鉴。
Anduin2017/HowToCook中文菜谱语料
中文菜谱冷启动数据。配合上面几个推荐项目，可以直接拼出中文版菜谱库。
slimane-lakehal/calorie_trackerPython CLI · SQLite
小而完整的 BMR/TDEE 参考实现，含食物库、饮食记录、体重追踪、CSV/JSON 导出。想快速验证代谢公式的正确性，读它比读大项目快。

8开发路线

阶段目标交付物
MVP算得准、记得住画像引擎（BMR/TDEE/宏量）+ 文本记录 + 成分表查询 + 当日营养汇总。数据源先用中国食物成分表 + HowToCook
V1有闭环体重趋势曲线（EMA）、周报、达成率、菜谱内容过滤推荐
V2有智能拍照识别 + 估重、约束优化排餐 + 采购清单、慢病规则引擎

顺序不能反。先把确定性计算做对，再上模型。很多项目死在反过来做——大模型给的数字没人敢信，又没法定位是哪一步错了。

9风险与合规

  • 医疗边界：只能做「营养参考」，不能做诊断、不能给治疗方案。每个结果页都要带免责声明，异常指标提示就医而非自行调整。
  • 特殊人群：孕妇、儿童、肾病、糖尿病、进食障碍史用户必须走保守策略（或明确拒答）。参考 OpenNutriTracker 的做法——它的断食计时器入口带内容警告并链接 BEAT / NEDA。
  • 热量下限：目标热量必须有硬下限，防止极端节食建议。男 1500 / 女 1200 kcal。
  • 数据授权：中国食物成分表商用需授权；USDA 与 Open Food Facts 是 CC0。
  • 隐私：健康数据属敏感个人信息，本地优先 / 加密存储，明确告知数据流向。
  • 估重误差披露：图像估算必须标注为「估算」，并提供手动修正入口。

10改造成微信小程序的可行性与代价

结论：技术上一行后端代码都不用改，但产品定位和主体资质必须调整，否则大概率卡在审核。前后端分离的分层在这里拿到了回报——换前端壳不影响算法层。

10.1 小程序端反而更强的三个点

wx.scanCode 扫条码
包装食品扫码是最高频入口。Web 端做扫码要自己接摄像头 + 解码库，体验差很多。小程序一个 API 搞定。
拍照上传链路短
chooseMedia 直接拿图 → uploadFile 上传 → 后端推理。这是本产品最核心的交互，移动端天然比 PC 合适。
分享与留存
微信内分享、无需安装、桌面图标，用户每天打开的心理成本远低于访问一个网址。

10.2 必须接受的硬约束

约束具体限制应对
类目与审核
（最大风险）		医疗服务属个人主体未开放类目，微信官方明确列示：在线问诊、预约挂号、非处方药交易等一律需企业主体 + 资质把产品定位成「饮食记录与营养查询工具」，服务类目选「工具 > 信息查询」。全站文案禁止出现治疗、诊断、疗效、用药建议、保证减重等词。首页固定免责声明
微信支付个人主体无法开通微信支付，也没法用手机号快速验证组件做免费工具。要收费必须企业主体 + 商户号
包体积主包 2 MB，总包 20 MB（含分包）模型一律放云端。几百 MB 的权重不可能塞进小程序
网络请求必须 HTTPS，且域名需在后台配置为 request 合法域名；自建服务器还需 ICP 备案方案 A：自建服务器 + 已备案域名 + FastAPI。方案 B：微信云开发 HTTP 云函数（Python 3），用平台默认域名可省去备案与运维

本地存储单个小程序 storage 上限约 10 MB画像、今日记录可缓存；历史数据与成分库走服务端
健康数据合规健康生理信息属《个人信息保护法》定义的敏感个人信息，需境内存储、单独同意配置《用户隐私保护指引》并声明采集项与用途；提供查询、更正、删除、注销入口

10.4 建议路径

  • 如果目标是课程项目 / 作品集评审：先做 Web。小程序要装开发者工具、配合法域名、等审核，迭代速度慢一档；评审看的是算法正确性和数据可追溯，不是端形态。
  • 如果目标是真上线给人用：直接做小程序更合适——核心入口（拍照 + 扫码）在移动端才成立。但先把后端 API 用 Web 或 Postman 调通，再写小程序端。
  • 跨端复用：后端完全复用。前端若想省事，用 Taro（React 语法，可编译到小程序 + H5）；若追求原生体验和小包体，写原生小程序。
  • 审核前置动作：开发前先去小程序后台确认服务类目能不能选「工具 > 信息查询」，并准备一份免责声明文案模板。别等功能做完才发现类目不符被驳回。
一句话总结风险：这个产品能不能上小程序，卡点不在技术，在「医疗器械/医疗服务」的定性。只要它看起来像在给医疗建议，个人主体就过不了。把它做成「记录 + 查询 + 统计」的工具，就能过。
