02阶段一 · 任务启动与需求澄清

Stage 01
先问清「给谁用、做到什么程度」，再动手
起点

项目一开始并没有直接写代码，而是先把三件事问清楚：使用场景（中文饮食、日常记录）、使用者（个人自查为主）、完成标准（能演示、能分享、能给别人用）。

这一步定下的最重要边界是产品定位：它是工具，不是医疗器械。所以全部文案避开治疗、诊断、疗效表述，页面底部常驻免责声明，接口返回里也带上 disclaimer 字段。

定边界比定功能更早。功能可以后加，定位错了后面全是返工。

03阶段二 · 功能模块的确立

Stage 02
8 个模块分 4 层，MVP 砍到 5 个
设计期

最初方案是 8 个模块：用户画像与代谢引擎、多模态饮食记录、食物成分与营养核算、菜谱与食物推荐、膳食计划与排餐、健康评估与风险预警、可视化与反馈闭环、营养知识问答 Agent。进入 MVP 阶段做了取舍：

模块取舍理由
代谢引擎（BMR / TDEE / 宏量）做整个系统的地基，所有目标值从它派生
中文食物库 + 自然语言解析做中文交互的核心差异点，不能照搬 USDA
营养核算与达标评估做用户每天真正会看的界面
菜谱推荐 + 三餐排餐做从「记录」走向「建议」的关键一步
网页界面 + API做决定这东西能不能演示、能不能给人用
拍照估卡（多模态）砍需训练数据与目标检测模型，开源方案误差 20–30%，MVP 投入产出比太低
体重趋势可视化只留算法EMA 与卡尔曼滤波已实现，图表界面留到 V2
知识问答 Agent（RAG）砍需向量库与权威指南语料，且存在医疗建议合规风险
一条贯穿全程的原则：所有数值必须由确定性代码计算，大语言模型不参与任何数字运算。 LLM 只负责组织语言、解释结果。营养数字一旦算错，用户信任立刻归零，而这类错误还极难定位。

04阶段三 · 资料的获取

Stage 03
数据来源可追溯，版权边界先划清
设计期

4.1 三类数据来源

  • 《中国食物成分表（第 6 版）》 —— 中文食物的权威基准。纸质/电子版有版权，本项目内置的是 100 条手工整理的学习演示数据，部分字段参考常见值，商用需取得授权。
  • Open Food Facts 与 USDA FoodData Central（均为 CC0）—— 可作为合法的完整数据替代来源，但仍需专业校验与字段清洗。
  • Food.com Recipes & Interactions（23 万菜谱 + 100 万交互）—— 菜谱推荐的语料候选。

4.2 数据设计上的两个关键决策

决策一：给食物条目加 portions 字段。 例如米饭 {"1碗": 150}。正是它让「一碗米饭」能被直接换算成 150 克，而不要求用户称重 —— 这是中文场景能否好用的分水岭。

决策二：菜谱营养不硬编码，由食材关联食物库自动推导。 改食物库，22 道菜的营养自动跟着变，不存在两处数据打架的问题。

4.3 规则类资料的调研

在评估「能否改成微信小程序」时专门查证了官方规则：医疗服务属于个人主体未开放类目；个人主体无法开通微信支付；小程序主包 2MB 限制意味着模型必须放云端；云开发的 Python 3 只存在于 HTTP 云函数分类下。这些结论直接反过来影响了产品定位 —— 工具属性而非医疗属性。

07阶段六 · 前后端开发

Stage 06
后端分层，前端单文件，同源省掉一半部署麻烦
开发期

7.1 后端（Python）

目录结构：formulas.py（代谢与营养公式）、food_db.py（中文食物库与自然语言解析）、analyzer.py（核算、达标评估、风险规则）、recommend.py（推荐）、planner.py（排餐与采购清单）、cli.py（中文命令行）、api.py（FastAPI）。

核心五个模块只用标准库，装不装依赖都能跑 —— 这条设计在后面排查「网页打不开」时起了关键作用：能立刻判断出问题不在业务代码，而在解释器选择。

API 设计上，GET / 直接返回网页，让页面和接口同源。这个决定在后面部署时省掉了跨域的一堆麻烦。

7.2 前端（原生 HTML / CSS / JS）

单文件、零构建、不引任何 CDN 资源，离线双击也能开。三个核心面板：身体档案（算 BMR / TDEE / 宏量）、饮食分析（中文文本 → 营养汇总与达标评估）、一日排餐（三餐 + 采购清单）。

  • 同源自适应：location.protocol === "file:" 时走本机固定端口，http(s):// 时走相对路径 —— 一份代码同时适配本地双击与云端托管。
  • 安全防护：所有 innerHTML 拼接都经 escapeHtml；用户标识从不进入 innerHTML，只赋给 input.value。
  • 降级可见：服务未启动时给出中文提示而不是白屏；按钮加 aria 状态、提交时按钮文案切「处理中…」。

8.3 修复是怎么被证明有效的

验证手段（不是「看着对」，是实打跑出来的）：
· 回归基线对照：检出旧版代码跑同一套测试脚手架，先复现问题，再用修复版跑一遍证明消失
· 边界攻击表：超长 200 字符、纯空格、空串、中文、含 / ? # 的脏值、XSS 载荷、localStorage 读写抛异常，逐条给「预期 / 实测 / 判定」
· 独立验证：修复者与验证者分离，验证者不重跑修复者跑过的用例，专攻未覆盖边界
· 线上逐字节比对：抓取线上页面算 sha256，与本地文件比对，确认发布的确实是最新代码
· 多访客端到端：两个陌生访客各自建档、记餐、排餐、删除，确认数据互不污染
过程中还识别出两个「假问题」，避免了错误修复：
① 审计脚本一度报「服务卡死」，实为脚本用管道接日志却从不读取，缓冲区写满导致服务端阻塞 —— 改日志落盘后恢复正常；
② 一个批次任务报「推送成功」，实际远端并未更新 —— 从此把「推送后必须核验远端 sha」定为固定动作。

理由说明

11阶段十 · 公网部署与多访客隔离

Stage 10
从「我电脑上能跑」到「发给别人就能用」
上线期

11.1 部署要解决的三件事

  1. 前端 API 地址同源自适应：原来写死 http://127.0.0.1:8000，部署后用户浏览器会把请求打到「自己电脑的 127.0.0.1」，页面能开但功能全废。改为按协议自适应。
  2. 新增云端启动入口 server.py：监听环境变量 PORT、绑定 0.0.0.0。实测 PORT=8011 时服务只监听 8011，8000 无服务，确认环境变量生效。
  3. 依赖与启动命令：pip install -r requirements.txt → python server.py。

11.2 多访客隔离（本轮最后修复的严重问题）

用户问「这个网站能在别人的电脑上用吗」，实测揭开两个叠加的问题：

问题 A · 整页 JS 崩溃。 脚本调用了未定义的函数，执行到那行即抛 ReferenceError，其后 400 多行（所有按钮的事件绑定）全不执行。页面能显示，点任何按钮都毫无反应。

问题 B · 全体访客共用同一份数据。 三个输入框硬编码 value="default"，JS 从不改动它 —— 意味着任何人拿到网址打开，看到的、能改的和能删的都是同一份记录。

修复方案：每位访客首次打开时生成一个专属身份标识（u- + 时间戳 base36 + 随机段），存在自己浏览器里并持久化；标识会做归一化（限长 40、剔除会切断 URL 路径的字符）但保留中文 —— 填「刘洺绮」照样能用。

线上实测结果（公网真实请求）：
· 线上页面与本地代码 sha256 完全一致（f5f3b8e6），确认发布的是最新版
· GET / → 200，49,489 字节，四个关键函数符号齐备
· /health → 200，100 条食物 / 22 道菜谱
· 身体档案 → TDEE 2617.6、减脂目标 2067.6 kcal、BMI 22.9
· 饮食分析「一碗米饭 150g 鸡胸肉」→ 正确解析 2 条（米饭 150 g + 鸡胸肉 100 g）
· 两个陌生访客各自建档：70 kg 那位 2594 kcal、95 kg 那位 2804 kcal；删掉一个的记录，另一个纹丝不动
· 中文标识、脏值 a/b?c=1（自动纠正为 abc=1）、隐私模式（localStorage 抛异常）全部正常

14工程方法沉淀

Lessons
这次任务里真正可复用的九条经验
跨项目适用
#经验来自哪次教训
1修完一层要再验一层。 排查要走到最底层，不能找到一个看起来合理的原因就收工「网页无法使用」只修到启动器就停，底下还压着整页 JS 崩溃
2单测通过 ≠ 能用。 语义方向、枚举一致性、真实输入格式，单测都覆盖不到，必须端到端实跑减脂被算成增肥，数学自洽但方向反了
3边界输入要主动构造。 0、负数、超长、纯空格、脏字符、存储抛异常，都是真实用户会踩到的体脂率填 0 直接把接口打成 500
4修复与验证要分开人。 验证者不重跑修复者的用例，专攻未覆盖边界，才会发现真问题独立回归纠正了错误的修复前提
5发布后要核验线上。 「已推送」「已部署」都是声明，不是事实，必须抓回来比对某次提交以为推上去了，实际远端没更新
6环境类问题往「依赖实测」上靠。 只看解释器存在与否，一定会选到裸环境启动器选中系统 Python 却缺 uvicorn
7Windows 批处理必须纯 ASCII + CRLF。 非 ASCII 字节会让解析整体错位，LF 会让标签定位失败setup_env.bat 崩成一堆碎片命令
8交付前做哈希比对。 桌面副本、压缩包、仓库三者最容易各自过期桌面副本与 zip 连续两轮被发现是旧版
9默认值即风险。 一个硬编码的 default 就足以让全部用户共用同一份数据所有访客写进同一个桶，互相覆盖

15已知限制与下一步

15.1 当前限制（诚实说明，非缺陷）

  1. 内置数据是演示数据。 100 条食物、22 道菜谱，未覆盖品牌差异、烹饪损耗、生熟重换算与个体差异，严禁用于实际健康决策。
  2. 排餐是贪心算法。 热量通常接近目标，但脂肪或碳水仍可能偏离 20–30%，生产版本应换整数规划。
  3. 状态存内存。 云端服务重启后记录会清空，没有账号、数据库与持久化。
  4. 无登录鉴权。 现在做到了「各自独立」，但不是「各自保密」—— 知道对方标识就能读到数据。正式多人使用需要加登录。
  5. 自然语言解析范围有限。 能识别内置名称、别名、克重与常见量词，不是通用语言模型。
  6. 无拍照识别、无协同过滤。 这两块都在 V2 范围。

15.2 下一步建议

  • 把食物库换成合法授权的全量数据（Sanotsu 项目或自建校验表）—— 这是从「演示」走向「可用」的第一步
  • 排餐改用整数规划，把宏量偏差压下来
  • 加 SQLite 持久化 + 简单账号，让记录不再丢失、数据真正隔离
  • 若要真做微信小程序：先确认「工具 > 信息查询」类目可选，文案避开治疗 / 诊断 / 疗效，个人主体不做任何支付
