Implementation Plan

SeekMeal · 领域小模型实施方案

把现有项目升级为「会对话的饮食助手」—— 用 0.6B–1.7B 开源小模型负责理解与表达，把全部数值计算继续交给已经验证过的确定性引擎。含工具协议、数据合成、QLoRA 训练配置与自动评估方案。

目标机型 RTX 5060 Laptop 8GB 基座 Qwen3-0.6B / 1.7B QLoRA 4-bit 数据自合成

01核心结论

不训"会算数的模型"，训"会听话的模型"。
SeekMeal 已经有一套确定性引擎（公式 / 食物库 / 推荐 / 排餐），它的计算是可信的。小模型要解决的问题只有一个：把用户随口说的一句中文，翻译成引擎能吃的结构化参数，再把引擎吐出来的数字组织成人话。
必须先破除的一个误解：没有个人能"从零训一个大模型"。哪怕 124M 参数的 GPT-2 级模型，从零预训练也要几十亿 token + 几千 GPU 小时。市面上所有 0.6B / 1.5B / 7B 模型无一例外都是拿开源基座做领域适配。所谓"做出我的小模型"，本质是领域微调。

2.1 三个必踩的坑

坑一 · C 盘只剩 19 GB。 模型权重、数据集、pip 缓存默认全落在 C 盘用户目录，一个 1.7B 模型加数据集就能撑爆。动手第一件事就是把缓存指到 E 盘（剩 139 GB）：
HF_HOME / TORCH_HOME / HF_HUB_CACHE / PIP_CACHE_DIR 全部改到 E:\。
坑二 · RTX 5060 是 Blackwell（sm_120）。 必须装 PyTorch 2.7+ 的 cu128 轮子。网上大半教程还停在 cu121，装完运行必报 no kernel image is available for execution —— 这个报错看起来像驱动问题，其实是版本不匹配，会浪费一整晚。
坑三 · 内存只有 15.3 GB（日常可用约 6 GB）。 数据处理必须流式读写，不要 json.load 整个数据集再遍历；训练时 dataloader 的 num_workers 别开太大。

03总体架构

三层职责严格分离。这条红线与现有项目"所有数值由确定性代码计算"的原则一脉相承，只是因为小模型能力更弱，收得更紧。

用户自然语言

│  意图识别 + 参数抽取           │   · 这句属于哪个意图
│  输出：{intent, args}         │   · 参数是什么
└─────────────────────────────┘
      │  结构化 JSON

│  analyzer / recommend /      │
│  planner / 体重趋势           │

└─────────────────────────────┘
      │

为什么表达层也要兜底模板？因为模型可能把 174 说成 147。做法是：模板先生成一份"标准答案"，模型只负责润色；如果润色结果里的数字与引擎输出不一致，直接丢弃模型输出，回退模板。这条校验让"模型胡说数字"从根上不可能发生。

04工具协议（理解层的输出契约）

理解层的输出不是自由文本，而是固定 schema 的 JSON。9 个工具直接对应引擎现有能力：

#工具名参数调用引擎
1set_profilesex, weight, height, age, activity, goal, weekly_delta_kg, body_fat_pct?compute_energy_budget() + macro_targets()
2log_mealtext, meal?FoodDB.parse_many() → DayLog.add()
3query_remaining（无）DayLog.remaining(target)
4query_summary（无）DayLog.totals() + evaluate() + risks()
5query_foodname, grams?FoodDB.search() / parse()
6recommend_recipesquery?, top_k?, avoid?RecipeBook.recommend()
7plan_day（无）plan_day() + DayPlan.shopping_list()
8log_weight / weight_trendweight? / （无）add_weight() / ema_series() + kalman_trend()
9delete_logindex?DayLog.remove()
—refuse_safetyreason不调用引擎，直接返回就医引导

4.1 输出格式

刻意不用完整的 OpenAI function-calling JSON（token 多、小模型容易生成错）。改用极简单行协议，训练和推理都用它：

{"intent": "log_meal", "args": {"text": "一碗米饭 150g鸡胸肉"}, "confidence": 0.95}
为什么极简？0.6B 模型生成嵌套 JSON 的容错率很低。字段越少、层级越浅，可解析率越高。实测中"两字段单层 JSON"比完整 function-calling 格式的解析成功率通常高出 15–25 个百分点。

05路线 B · 打通闭环（先做，1–2 天）

Stage B · 不训练
用现成小模型 + 提示词跑通整条链路
目的：验证架构可行，且为路线 A 提供对照基线
  1. 工程骨架：SeekMeal/llm/ 目录，含 tools.py（工具层）、prompt.py（系统提示词）、router.py（调度器）、backend.py（模型后端抽象）。
  2. 后端抽象：定义统一接口 generate(messages) -> str。先实现两个：
    • RuleBackend —— 纯规则模拟器，不依赖任何模型，用来验证链路本身
    • LlamaCppBackend / OllamaBackend —— 接真实小模型
  3. 跑通闭环：规则后端先把 9 个工具全部打通，确认「理解 → 计算 → 表达 → 数字校验」四步都对。
  4. 插入真模型：下载 Qwen3-0.6B GGUF（约 400 MB），换后端，对比两者差异。
  5. 建立基线：记录提示词版在测试集上的意图准确率 —— 这就是路线 A 要超越的数字。
这一步的产出本身就是可用的。 提示词版已经能把"我今晚还能吃多少"变成真实回答，不需要等训练完成。

06路线 A · 领域微调（核心，2–4 周）

Stage A · 核心
用引擎自合成数据，QLoRA 训出"你的模型"
目的：让 1.7B 在意图识别与参数抽取上超过提示词版

6.1 数据从哪来 —— 这是本项目最大的优势

别人做领域微调卡在数据：人工标注几千条问答又贵又不可靠。而 SeekMeal 自带一台确定性引擎，可以机器生成"答案 100% 正确"的问答对：

随机采样参数  →  套问题模板  →  调用真实引擎  →  (问题, 答案) 对
                                    ↑
                        答案由代码算出，绝对正确、可自动验证
环节做法
参数采样在合理区间随机：体重 45–110 kg、身高 150–195 cm、年龄 16–65、活动水平 5 档、目标 3 种、每周变化 0–1.5 kg
问题模板每个意图 20–40 条口语化模板，覆盖不同说法（"我还能吃多少"/"今天还剩多少额度"/"还差多少热量"）
答案生成调用真引擎算，再由模板渲染成自然语言（不是让大模型编）
难例注入故意加入：含糊表达、错别字、多意图混说、超范围提问、涉及疾病需拒答
规模1.5–2 万条（领域窄，不需要百万级）
切分训练 / 验证 / 测试 = 8 : 1 : 1，按参数组合切分而非随机切分，防泄漏

LoRA alpha3232惯例取 2r
lora_dropout0.05—

· LLaMA-Factory —— 有 WebUI，配置文件驱动，不写训练脚本，适合先跑通；
· Unsloth —— 同显存下更快、占用更低，适合 8GB 临界场景，但需要写少量代码。

6.4 训练目标：只优化"理解"，不碰"表达"

训练时的 loss 只算在模型的输出段（即那段 JSON），用户输入与工具返回结果都 mask 掉。理由：表达层的质量由模板保证，让模型去学"怎么把 174 kcal 说得好听"性价比很低，而且它会开始幻想数字。

样本结构（训练时只对 assistant 段计 loss）
<|im_start|>system
你是 SeekMeal 的意图解析器……只输出 JSON。<|im_end|>
<|im_start|>user
我今晚还能吃多少<|im_end|>
<|im_start|>assistant
{"intent":"query_remaining","args":{}}<|im_end|>   ← 只有这段算 loss

07评估方案（可自动判分）

Evaluation
四个指标，全部机器判定，不靠人眼
这也是本项目相对其他微调项目的优势
指标怎么算目标线
JSON 可解析率模型输出能被 json.loads 且字段合法的比例≥ 99%
意图准确率预测 intent 与标注 intent 完全一致的比例≥ 95%（提示词版基线约 80–88%）
参数抽取 F1args 各字段逐字段比对（数值容差 ±0.5）≥ 90%
端到端成功率一次对话中链路无异常完成任务的比例≥ 90%
安全拒答率医疗类问题被正确拒答的比例= 100%（硬指标）
幻觉数字率回答中出现的数字在引擎输出里找不到对应来源= 0（由校验层强制保证）
为什么能自动判分？因为标准答案由引擎生成，判定也是拿引擎复算一遍。不需要人工标注测试集，也不需要另一个大模型当裁判——确定性引擎本身就是唯一真相。这是很多领域微调项目做不到的。

rem 2) 建训练专用环境（与 seekmeal 运行环境隔离）
python -m venv %USERPROFILE%\.workbuddy\binaries\python\envs\seekmeal-llm

rem 3) 装 Blackwell 对应的 torch（cu128，必须 2.7+）
pip install torch --index-url https://download.pytorch.org/whl/cu128

rem 4) 训练栈
pip install transformers datasets peft trl accelerate bitsandbytes

rem 5) 推理量化导出（可选）
pip install llama-cpp-python
环境隔离说明：训练环境单独建 (seekmeal-llm)，不要装进现有的 envs\seekmeal。原因：torch + CUDA 全家桶好几个 GB，混进去会让原本轻量的运行环境变重；而且两者坏掉的时机不同，隔离后训练环境炸了不影响线上服务。

11风险与回退

风险概率应对
1.7B 训练显存不足中降到 0.6B；或 seq_len 降到 768、batch=1、开启梯度检查点
合成数据过于模板化，模型只会背模板高模板多样性做到每个意图 20–40 条；注入错别字/口语/混说；测试集用未见过的表达方式
模型学会"自己算数"并算错中训练时只在 JSON 段计 loss，不让它看数字；表达层加数字一致性校验，不一致即回退模板
Blackwell 兼容性问题卡住中先只用 CPU/GGUF 走通推理与数据合成；训练再单独解决 CUDA
折腾几周效果不如提示词版中这本身也是结论。提示词版已经能用，微调版是加分项，不是必需品 —— 架构上两者可随时切换
最重要的一条设计保障：整条链路是可摘除的。小模型只是一个新增模块，接不上、效果差、显存不够，摘掉之后 SeekMeal 还是原来那个能用的 SeekMeal。不做"要么全成要么全废"的赌注。
