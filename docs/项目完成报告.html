1. 功能模块的确立

项目启动时先做了模块划分，而不是直接写代码。最初的方案是 8 个模块、分 4 层：用户画像与代谢引擎、多模态饮食记录、食物成分与营养核算、菜谱与食物推荐、膳食计划与排餐、健康评估与风险预警、可视化与反馈闭环、营养知识问答 Agent。

进入 MVP 阶段时做了取舍，砍掉三个、聚焦五个：

模块去留理由
代谢引擎（BMR/TDEE/宏量）✅ 做整个系统的地基，所有目标值从它派生
中文食物库 + 自然语言解析✅ 做中文交互的核心差异点，不能照搬 USDA
营养核算与达标评估✅ 做用户每天真正会看的界面
菜谱推荐 + 三餐排餐✅ 做从"记录"走向"建议"的关键一步
网页界面 + API✅ 做决定这个东西能不能演示、能不能给人用
拍照估卡（多模态）❌ 砍需训练数据与目标检测模型，开源方案误差 20–30%，MVP 阶段投入产出比太低
体重趋势可视化⚠️ 只留算法EMA 与卡尔曼滤波已实现，图表界面留到 V2
知识问答 Agent（RAG）❌ 砍需要向量库与权威指南语料，且存在医疗建议合规风险
一条贯穿全程的原则：所有数值必须由确定性代码计算，大语言模型不参与任何数字运算。 LLM 只负责组织语言、解释结果。营养数字一旦算错，用户信任立刻归零，而这类错误还极难定位。

2. 资料的获取

2.1 营养数据来源

  • 《中国食物成分表（第 6 版）》：中文食物的权威基准。纸质/电子版有版权，本项目内置的是 100 条手工整理的学习演示数据，部分字段参考常见值，商用需取得授权。
  • Open Food Facts（CC0）与 USDA FoodData Central（CC0）：可作为合法的完整数据替代来源，但仍需专业校验与字段清洗。
  • Food.com Recipes & Interactions（23 万菜谱 + 100 万交互）：菜谱推荐的语料候选。

2.2 数据设计上的关键决策

食物条目里加了一个 portions 字段，例如米饭的 {"1碗": 150}。正是它让「一碗米饭」能被直接换算成 150 克，而不要求用户称重——这是中文场景能否好用的分水岭。

另一个决策：菜谱的营养不硬编码，而是由食材关联食物库自动推导。改食物库，22 道菜的营养自动跟着变，不存在两处数据打架的问题。

2.3 规则类资料的调研

在评估"能否改成微信小程序"时，专门查证了微信官方规则：医疗服务属于个人主体未开放类目；个人主体无法开通微信支付；小程序主包 2MB 限制模型必须放云端；云开发的 Python 3 只存在于 HTTP 云函数分类下。这些结论直接影响了产品定位——工具属性而非医疗属性。

三餐排餐贪心 + 份量缩放（0.5–2.0×），每餐可配多道菜中餐一餐是"主食+菜"的组合，单道菜撑不起一顿
排餐踩过的坑：第一版每餐只选一道菜，结果一日总热量只有 1153 kcal，而目标是 2255——差了一半。改成每餐可配多道菜并加份量缩放后，实测对齐到 1884 / 目标 1882，误差 <1%。

5. 后端与前端的开发

5.1 后端（Python）

目录结构：formulas.py（代谢与营养公式）、food_db.py（中文食物库与自然语言解析）、analyzer.py（核算、达标评估、风险规则）、recommend.py（推荐）、planner.py（排餐与采购清单）、cli.py（中文命令行）、api.py（FastAPI）。核心五个模块只用标准库，装不装依赖都能跑。

API 设计上，GET / 直接返回网页，让页面和接口同源——这个决定在后面部署时省掉了跨域的一堆麻烦。

5.2 前端（原生 HTML/CSS/JS）

单文件、零构建、不引任何 CDN 资源，离线双击也能开。三个核心面板：身体档案（算 BMR/TDEE/宏量）、饮食分析（中文文本 → 营养汇总与达标评估）、一日排餐（三餐 + 采购清单）。服务未启动时会给出中文降级提示而不是白屏，底部常驻免责声明。

6. 测试、验收与三个真 Bug

27 项单元测试全通过。但真正暴露问题的不是单测，而是端到端实跑——起真实服务打真实请求。三个 Bug 都是这么发现的，看代码一个也看不出来：

Bug 1 · 活动水平枚举不一致
网页下拉框用 active/very_active，后端只认 sedentary/light/moderate/high/very_high，选到那两档直接 400，功能不可用。

Bug 2 · 减脂算成增肥（最严重）
weekly_delta_kg 约定"正数增重、负数减重"，但用户在网页选「减脂」再填「每周 0.4kg」，算出 3073 kcal，比 TDEE 2633 高出 440——等于让用户增肥。改为由 goal 决定方向后，正确输出 2193 kcal。
教训单测只验证数学自洽，验证不了语义方向。这类引擎必须专门加"方向断言"。

Bug 3 · 中文输入静默丢数据
分隔正则要求两个以上空格，「一碗米饭 鸡胸肉100g」只记了鸡胸肉，米饭被丢掉；另一处「150g 鸡胸肉」被切成两段，克重丢成默认 100g。最终改为"空格后跟非数字才切分"＋数量片段合并。

7. 部署与最终呈现

部署到公网需要解决三件事：

  1. 前端 API 地址必须同源自适应：原来写死 http://127.0.0.1:8000，部署后用户浏览器会把请求打到"自己电脑的 127.0.0.1"，页面能开但功能全废。改为 file:// 打开时走本机、http(s):// 打开时走相对路径。
  2. 新增云端启动入口 server.py：监听环境变量 PORT、绑定 0.0.0.0。实测 PORT=8011 时服务只监听 8011，8000 无服务，确认环境变量生效。
  3. 依赖与启动命令：pip install -r requirements.txt → python server.py。
线上实测结果（公网真实请求）：
· GET / → 200，返回 37,201 字节网页
· 身体档案 → BMI 22.9、BMR 1698.8、TDEE 2633.1、减脂目标 2193.1 kcal
· 饮食分析「一碗米饭 鸡胸肉100g」→ 正确解析 2 条（米饭 150g + 鸡胸肉 100g）
· 一日排餐 → 早餐燕麦牛奶早餐杯 566 kcal、午餐蛋炒饭 753 kcal、晚餐香煎三文鱼配糙米饭 565 kcal，合计 1884 kcal，采购清单 10 项
· 风险提示正常触发："膳食纤维仅 0.4 g，建议增加蔬菜、全谷物与豆类"

8. 已知限制

  1. 内置数据是演示数据。100 条食物、22 道菜谱，未覆盖品牌差异、烹饪损耗、生熟重换算与个体差异，严禁用于实际健康决策。
  2. 排餐是贪心算法。热量通常接近目标，但脂肪或碳水仍可能偏离 20–30%，生产版本应换整数规划。
  3. 状态存内存。云端服务重启后记录会清空，没有账号、数据库与持久化。
  4. 自然语言解析范围有限。能识别内置名称、别名、克重与常见量词，不是通用语言模型。
  5. 无拍照识别、无协同过滤，这两块都在 V2 范围。
